# DockStart 全功能扩展计划书

> 目标：在不牺牲 DockStart 现有“现代化、简洁、引导清晰、开箱即用”体验的前提下，逐步补齐 AutoDock Vina 已有但 DockStart 尚未完整支持的功能，并建立可持续扩展的对接协议架构。

- 项目仓库：<https://github.com/xuxinxi14/DockStart>
- 当前基线：DockStart v0.12.0
- 当前内置核心：AutoDock Vina 1.2.7
- 计划性质：产品路线图 + 技术架构方案 + 开发实施计划 + 验收标准
- 实施原则：分阶段发布，不进行一次性大重写

---

## 1. 项目背景

DockStart 当前已经形成较完整的标准分子对接流程：

1. 创建或打开项目；
2. 导入或准备受体、配体；
3. 设置对接 Box；
4. 设置 Vina/Vinardo 常用参数；
5. 运行前检查；
6. 执行 AutoDock Vina；
7. 查看构象、分数和 RMSD；
8. 导出 CSV 与 Markdown 实验记录。

现阶段 DockStart 的主要优势不是修改对接算法，而是把分散的命令行工具、文件格式、参数设置和结果归档整理成清晰、可追踪、适合初学者的本地工作流。

下一阶段不应简单地把 AutoDock Vina 的全部命令行参数堆进一个“高级设置”页面，而应把不同科学用途拆分成明确的“对接协议”，为每种协议提供独立的输入要求、准备流程、参数、运行前检查、结果解析和报告模板。

---

## 2. 总体目标

### 2.1 产品目标

将 DockStart 从“标准刚性单配体对接工作台”逐步升级为：

> 面向 AutoDock Vina 生态的现代化、本地化、可追溯分子对接工作台。

完成后应覆盖：

- 标准刚性单配体对接；
- Vina 与 Vinardo；
- 高级搜索参数；
- `score_only` 现有姿势评分；
- `local_only` 局部优化；
- 批量虚拟筛选；
- 柔性侧链对接；
- 大环配体工作流；
- AutoDock4 affinity maps；
- AutoDock4 评分；
- 多配体共同对接；
- AD4Zn 专用协议；
- 水合对接；
- 外部 maps 导入、生成与复用；
- 完整任务队列、结果汇总和审计记录。

### 2.2 非目标

本计划不包含：

- 修改 AutoDock Vina 核心算法；
- 自研新的 scoring function；
- 将 docking score 描述为真实结合自由能；
- 自动生成药效、安全性或临床结论；
- 分子动力学模拟；
- QM/MM；
- 自动论文生成；
- 无人工确认的全自动受体修复；
- 无依据的自动质子化、电荷或结合位点判断。

### 2.3 成功标准

1. 初学者仍能在默认流程中完成标准对接，不被高级功能干扰。
2. 高级用户可以选择明确的协议，而不是手动拼装命令行参数。
3. 所有运行均保存输入、配置、命令、工具版本、日志、输出和哈希。
4. 每种协议都有独立的科学边界说明与失败提示。
5. Basic 安装包保持精简；Assisted 安装包继续开箱即用。
6. 复杂功能采用逐级披露，不破坏现有现代化界面。
7. 项目文件具有向前迁移、向后保护和异常恢复能力。

## 3. 产品设计原则

### 3.1 默认流程必须保持简单

默认首页和新建项目入口只突出三类常用场景：

- 标准小分子对接；
- 批量虚拟筛选；
- 现有姿势评分与优化。

柔性侧链、AutoDock4、AD4Zn、水合对接等高级协议放入“更多协议”，不在首页同时展示大量入口。

默认标准对接仍只要求用户理解：

- 受体；
- 配体；
- Box；
- 搜索彻底程度；
- 构象数量；
- 开始运行。

### 3.2 使用“协议”而不是“参数堆叠”

不建议继续把全部功能加入现有 `VinaSettings`。建议建立协议类型：

```text
rigid_single
batch_screening
score_only
local_only
flexible_sidechain
macrocycle
ad4_maps
multiple_ligands
ad4zn
hydrated
```

每种协议拥有：

- 独立输入模型；
- 独立工具依赖；
- 独立准备流程；
- 独立参数模型；
- 独立前置检查；
- 独立命令生成器；
- 独立输出解析器；
- 独立报告章节；
- 独立科学风险提示。

### 3.3 逐级披露

每个协议的参数页面分成三层：

#### 基础参数

只显示多数用户必须设置的内容。

#### 推荐设置

提供可解释预设：

- 快速预览；
- 标准；
- 深度搜索；
- 自定义。

#### 专家参数

折叠显示：

- `min_rmsd`；
- `max_evals`；
- `spacing`；
- `verbosity`；
- `no_refine`；
- `unbound_energy`；
- scoring weights 等。

专家参数必须显示默认值、单位、作用、风险、可比性影响，并提供“一键恢复默认值”。

### 3.4 自动化只能代替机械步骤，不能代替科学判断

允许自动完成：

- 路径管理；
- 文件复制；
- 配置生成；
- 工具检测；
- 格式检查；
- 任务排队；
- 日志归档；
- 结果汇总；
- 哈希记录。

必须要求人工确认：

- 受体链选择；
- 缺失残基处理；
- 水分子、金属、辅因子保留；
- 质子化状态；
- 配体形式电荷；
- 互变异构体；
- 柔性残基选择；
- 大环断环位置；
- Zn 配位环境；
- Box 是否覆盖真实研究位点。

### 3.5 保持本地优先

除主动下载 RCSB/PubChem 数据外：

- 结构准备在本机完成；
- 对接在本机完成；
- 项目数据在本机保存；
- 诊断在本机生成；
- 不上传私有结构；
- 不依赖云端账户才能运行。

## 4. 总体架构方案

### 4.1 协议注册中心

新增统一协议接口：

```python
class DockingProtocol:
    protocol_id: str
    display_name: str
    maturity: str
    required_tools: list[str]

    def validate_inputs(...)
    def prepare_inputs(...)
    def build_config(...)
    def build_command(...)
    def preflight(...)
    def parse_outputs(...)
    def build_report(...)
```

协议注册中心负责：

- 返回当前可用协议；
- 判断 Basic/Assisted 是否满足依赖；
- 返回协议说明；
- 返回表单 schema；
- 调用对应运行适配器；
- 统一保存审计信息。

### 4.2 项目数据模型升级

建议将当前项目 schema 升级为 v2：

```json
{
  "schema_version": 2,
  "project_name": "...",
  "protocol": {
    "id": "rigid_single",
    "version": 1,
    "maturity": "stable"
  },
  "inputs": {},
  "preparation": {},
  "search_space": {},
  "parameters": {},
  "runs": []
}
```

要求：

- 保留 v1 项目迁移；
- 旧项目默认映射为 `rigid_single`；
- 迁移前自动备份；
- 未知字段继续保留；
- 高版本项目不得被低版本程序强行改写；
- 每次运行保存协议版本，避免以后逻辑变化影响历史重现。

### 4.3 统一运行任务模型

所有协议使用统一状态：

```text
created
preparing
queued
running
cancelling
cancelled
finished
failed
interrupted
recoverable
```

任务记录至少包含：

- task_id / run_id；
- protocol_id；
- 输入快照；
- 配置快照；
- 命令数组；
- 工具版本与哈希；
- 开始、结束时间；
- PID 与进程身份；
- stdout/stderr/log；
- 输出文件；
- 解析结果；
- 错误代码；
- 重试来源；
- 取消原因；
- 恢复状态。

### 4.4 统一结果模型

```text
ligand_id
pose_id
affinity
rmsd_lb
rmsd_ub
status
warning_count
output_file
protocol
scoring_function
```

协议可附加扩展字段，例如柔性残基、大环断环键、maps 信息、Zn 配位参数、水合状态和多配体成员。

# 阶段 1：高级参数与轻量运行模式

## 目标

优先加入实现成本较低、科研用途明确的 Vina 原生能力。

当前状态：**姿势评价、局部优化定量比较与首批高级参数源码闭环完成，尚未发布**。`score_only` 已形成单点评分闭环；新准备的 `local_only` 已形成输入基线评分、局部优化、评分差、几何位移、同场 3D 叠合和报告闭环；`max_evals`、`min_rmsd`、`spacing`、`verbosity`、`no_refine`、`force_even_voxels` 与 `unbound_energy` 已接入单次运行，串行批量全局对接也继承其中除 `unbound_energy` 外的六项适用参数。`randomize_only` 仍未实现。本轮不修改 DockStart 版本号，也不改变任何既有安装包或发布状态。

## 功能范围

### 1.1 高级 Vina 参数

新增：

- `min_rmsd`；
- `max_evals`；
- `spacing`；
- `verbosity`。

- `no_refine`；
- `force_even_voxels`；
- `unbound_energy`。

默认行为与 Vina 保持一致；`unbound_energy` 未显式设置时保持 `None` 并省略配置项，不把 Vina 内部默认行为伪装成数值。

当前已接入：

- `max_evals` 和 `min_rmsd` 仅用于全局搜索；评价模式不写入无效参数；
- `spacing` 用于现场计算的 Vina/Vinardo 网格，AutoDock4 maps 下不写入；
- GUI 开放标准与详细两档日志；`local_only + verbosity = 2` 按明确边界解析优化前后能量块；
- `no_refine` 和 `force_even_voxels` 默认关闭，只在当前 Vina 的 `--help_advanced` 精确声明且达到最低安全版本时可启用；准备与执行阶段都会复核；
- `no_refine` 改用网格完成最终优化和评分，结果只与同设置运行比较；`force_even_voxels` 的取整会进入实际网格点数与资源估算；
- `unbound_energy` 默认留空，只在 Vina/Vinardo、刚性单配体 `score_only` 中写入；显式 `0` 与留空不同，只接受有限数值。最低门槛按 SemVer 与稳定版 Vina 1.2.4 比较，因此 `1.2.4-rc1` 不满足门禁；
- 对新生成的 `score_only` run，结果分析先核对日志 SHA256；显式参考还要求第 (1)～(4) 项编号和数值有效、第 (4) 项与冻结值一致，并验证总评分为 `(1) + (2) + (3) - (4)`。生成后的 `evaluation.json` 也以 SHA256 绑定到 run，读取和报告前都会复核。全局对接、`local_only`、柔性受体、AutoDock4 maps 和批量筛选均不使用该项；
- Box、spacing 与可移动原子类型联合估算网格内存，超出资源保护上限时在启动前阻断；
- 项目、配置、run 快照、批量队列快照、逐配体 config、报告、归档协议指纹、旧项目默认值和旧基础参数调用兼容均已覆盖。

### 1.2 `score_only`

以独立运行模式评价现有受体—配体姿势，不进行全局搜索，也不生成新构象。

本轮已接入：

- 保存 `run_mode = score_only` 的项目选择和不可变运行快照；
- 用户必须在同场 3D 视图复核输入姿势；确认记录绑定本次运行实际使用的刚性受体、可选柔性侧链与配体 SHA256，任一输入替换或柔性受体重建后失效，未确认时后端拒绝准备新 run；
- Vina/Vinardo 可使用项目 Box，也可显式启用 autobox；
- AutoDock4 maps 运行时由 maps 网格定义范围，autobox 必须关闭；
- 解析 Vina 能量分项，写入独立的 `evaluation.json`；
- 结果页显示姿势评分摘要与能量分项，不生成虚假的 pose 排名、Mode 1 或 RMSD；
- Viewer 查看的是本次运行冻结的输入配体快照；
- 输出独立的姿势评价 Markdown 报告。

未纳入本轮：自定义评分权重等其余专家参数。

### 1.3 `local_only`

以独立运行模式从输入姿势附近执行局部优化。它只探索输入姿势邻域，不等同于全局对接，也不能解释为已搜索整个 Box。

本轮已接入：

- 输入姿势预览；
- 普通 Box 或可选 autobox；AutoDock4 maps 下同样关闭 autobox；
- 同一不可变输入与配置下依次执行 `score_only` 基线和 `local_only`，分别保存阶段命令、时间、退出码、stdout、stderr、log 与 SHA256；
- 输出并查看 `optimized.pdbqt`；
- 解析输入与优化后能量分项，固定按“优化后－输入”计算评分差，写入独立的 `evaluation.json`；
- 按 Meeko SMILES 原子索引或严格 PDBQT 原子身份匹配，计算同一受体坐标系内不做对齐的重原子 RMSD、平均/最大位移与质心位移；
- 现代双阶段 run 的结果页默认在同一 3D 场景叠合冻结的受体、输入姿势与优化后姿势，并可单独显示任一姿势；叠合不做额外对齐，Viewer 读取前复核关键 SHA256；
- 基线失败或取消后不启动局部优化；日志或输出哈希变化时拒绝发布比较；
- 旧单阶段 `local_only` run 保持可读，缺少输入基线时明确显示不可比较，不填零。

未纳入本轮：轨迹动画、对称性重映射，以及把位移指标解释成共晶验证 RMSD。

### 1.4 `randomize_only`

作为专家工具，不作为主要首页入口。明确提示随机化姿势不是 docking 结果。

Vina 1.2.7 实测中 `randomize_only` 不遵守 CLI `--seed`，相同 seed 不能重放输出；同时它不产生评分或局部优化结果。因此它不作为高级参数之后的默认下一批能力，除非上游可复现性改变，或产品明确接受“不可复现的受限专家工具”定位。

## UI 设计

当前源码在统一的 Vina 运行工作台提供运行任务切换：

- 全局对接；
- 只评分；
- 局部优化。

切换只评分或局部优化后，界面隐藏仅适用于全局搜索的参数，并显示 autobox 选项和对应科学边界。帮助页、新建项目页和项目总览已经提供独立任务入口；文件来源仍按已有 PDBQT、原始结构转换和 Demo 单独选择。评价模式不开放独立 PubChem 在线构象入口，还要求用户在同场 3D 视图确认当前配体姿势，确认记录与本次运行实际使用的刚性受体、可选柔性侧链及配体 PDBQT 的 SHA256 绑定。标准对接参数页保持原有默认行为；`randomize_only` 仍不作为主要入口。

## 验收标准

- 默认标准流程不增加必填项；
- `score_only` / `local_only` 缺少当前输入姿势确认、确认哈希与现有文件不一致或任一输入不可读时，配置和 run 准备都必须阻断；
- prepared 评价 run 在执行前必须再次核对冻结确认与本次刚性受体、可选柔性侧链及配体输入快照；缺失、格式错误或 SHA256 不一致时不得启动 Vina；
- 新参数正确写入运行快照；
- 需要门禁的选项能力未知、不满足最低版本或未被高级帮助声明时必须在启动 Vina 前阻断；其中 `autobox` 要求稳定版 Vina 1.2.3 或更高版本；
- 准备后替换为不兼容的 Vina 可执行文件时，执行阶段必须再次阻断；
- 新生成的 `score_only` 日志缺少可信 SHA256、文件变化或哈希不一致时，不生成姿势评分结果；
- 显式 `unbound_energy` 只有在第 (1)～(4) 项完整、编号正确、第 (4) 项与快照一致且总评分满足 `(1) + (2) + (3) - (4)` 时，才记录为显式参考评分；
- `evaluation.json` 缺少可信 SHA256、内容变化或显式参考值类型非法时，结果页与报告均拒绝读取；
- `score_only` 不生成虚假的 pose 排名表；
- `score_only` 成功不依赖 `out.pdbqt`，并保留不可变输入姿势用于查看；
- `local_only` 正确保存优化后结构；
- 新 `local_only` 必须按顺序完成输入评分与局部优化，两阶段使用同一冻结输入、配置与评分协议；
- 差值定义、原子映射方法和“未对齐”边界在结果页与报告中明确可见；
- 任一阶段失败、取消、工具二进制变化或关键日志篡改时不生成可比较结论；
- 报告明确区分全局对接、评分和局部优化；
- 不同 scoring function 的分值不横向混排。

兼容性与发布边界：

- 当前仍使用 schema v1 的兼容扩展字段 `docking_protocol.run_mode` 与 `docking_protocol.autobox`，没有为了本功能迁移或重写用户项目；
- 旧项目缺少这些字段时固定解释为 `run_mode = dock`、`autobox = false`，继续执行原有全局对接；
- 已完成的历史评价 run 不因缺少新确认字段而停止读取；旧评价项目再次创建 run 时必须先对当前输入完成哈希绑定确认，旧的未执行 prepared 评价 run 缺少该记录时必须重新准备；
- 旧项目缺少七项高级参数时恢复各项默认行为；`unbound_energy` 缺失时保持空值并不写入配置。旧调用方只提交基础参数时不覆盖已经保存的高级值；
- 批量筛选仍固定使用全局对接，不继承单次运行的姿势评价模式；
- 批量筛选继承适用于全局对接的六项高级参数，并冻结到队列、逐配体 config、整批报告和归档协议指纹；两个专家开关继续执行当前 Vina 能力门禁及执行前复核，`unbound_energy` 不进入批量；
- 本轮已通过源码树内置 Vina 1.2.7 的真实双阶段回归、两个专家开关 smoke 与显式 `unbound_energy` 评分闭环，并覆盖基线失败、阶段间取消、现代 `score_only` 日志 SHA256 篡改、未结合态项号/快照/能量平衡不一致、严格原子映射、能力门禁和旧 run 兼容；这不代表 Basic/Assisted 安装包已经包含或验证该能力；
- 发布前仍需完成 Basic/Assisted 安装态回归、用户文档截图、安装升级路径和发布材料复核。

# 阶段 2：批量虚拟筛选

## 目标

建立 DockStart 最重要的扩展能力：单受体、多配体的本地批量筛选工作流。

## 功能范围

### 2.0 当前实现状态（v0.12.2 源码）

已完成的闭环包括：多文件或目录递归导入 PDBQT/SDF/MOL、多分子 SDF 逐记录准备与导入预览、固定受体/Box/基础参数与六项适用高级参数快照、稳定串行队列、逐项独立 config 与 attempt、失败重试、安全取消与恢复、归档、全量 CSV、Top N、完整结果检索/筛选/排序/分页、逐配体最佳构象查看、批量 Markdown 实验记录、归档列表与只读历史结果浏览、双归档严格只读比较，以及单归档可校验 ZIP 导出。

逐配体 Viewer 使用本次筛选冻结的受体与该 item 成功 attempt 的输出；归档 Viewer 还按合法 `archive_id` 将读取范围限定在所选归档，只开放成功配体的 Mode 1。新任务保存输出 SHA256，哈希不一致时拒绝显示；旧归档没有输出哈希时保留可读，但标记为历史未完全验证。前端仅在用户点击某个成功项时加载其结构，不一次性加载整个配体库。

归档索引会保留损坏条目及错误原因，但在归档标识、清单、状态哈希或目录边界校验失败时阻止详情和 3D 读取。归档保持只读，不能恢复为活动队列，也不提供编辑、重试或取消。

双归档比较要求恰好选择两个不同且有效的归档，选择顺序固定为基线和对照。后端先实际核对两批冻结受体及全部冻结配体输入的文件大小与 SHA256，再仅按 ligand 输入 SHA256 建立逐项匹配；重复 SHA256 标记为 `ambiguous`。协议指纹覆盖受体 SHA256、评分函数、Box 六项、Vina 版本与二进制 SHA256，`exhaustiveness`、`num_modes`、`energy_range`、`cpu`、`seed`，以及 `max_evals`、`min_rmsd`、`spacing`、`verbosity`、`no_refine`、`force_even_voxels`。只有协议相同、身份唯一、两侧成功且评分与排名有效时，才计算 `Δ = 对照－基线`；协议不一致仍并排显示但不计算差值。整个比较过程只读，不修改 `project.json` 或归档内容。

单归档 ZIP 导出只接受安全可读的历史归档，并以 allowlist 形成 `payload/<archive_id>/`。根清单 `dockstart_screening_export.json` 记录精确成员、逐文件大小与 SHA256、payload 树哈希、源完整性状态及兼容警告；写入后重新执行 ZIP CRC、成员集合和逐文件哈希验证。现代归档会把 `attempt.json` 与冻结 attempt 记录绑定，并为构象、完整汇总、Top N 和 Markdown 实验记录保存及核对历史大小与 SHA256；旧归档缺少这些凭据时允许保留部分验证状态导出，但不会用导出时的新哈希升级成现代完整验证。GUI 始终按“不覆盖”发布；目标已存在时保留原文件并要求另选名称，避免保存对话框与实际写入之间的覆盖竞态。包不包含 Vina 二进制、活动队列、项目当前状态或 staging，不能直接导入或恢复运行；已有审计 JSON 可能含绝对本机路径，因此默认不匿名。清单哈希验证导出包字节，不是数字签名或历史真实性证明。

配体库导入现在先在启动 RDKit/Meeko 前盘点容器大小、逻辑记录数和单记录大小。SDF 中每条记录保持 1-based 原始位置，单条读取或准备失败只进入导入预览，不会吞掉其他有效分子。准备后的 PDBQT 按精确字节 SHA256 去重，`staged` 只返回可安全建队的唯一项；重复、失败和每条源文件/record SHA256 仍保存在 additive staging index 中。创建队列时会交叉核对 staging 文件身份，并把 record 级来源和显示名冻结到 `screening.json` 与后续 `attempt.json`。该增量不迁移 `project.json` 或 `screening.json` schema，也不改变发布版本号。

仍未完成的范围包括：导入表的形式电荷/重原子/可旋转键统计、失败准备项单独重试与清单导出、原始 record 字节的项目内冻结及其驱动的批量 SDF 汇总、并行队列、单项取消、归档删除、ZIP 导入/恢复与多个构象并排查看。后续规划不得再把已完成部分写成从零开发。

## 验收标准

- 项目当前硬上限为 500 个配体；已完成 50 个真实 Vina 子进程压力测试，后续应以测得的内存和 GUI 响应为依据增加 100/500 项门禁；
- 单个配体失败不阻塞整个队列；
- 中断后可识别已完成项；
- 不覆盖历史结果；
- 总 CPU 不超过用户上限；
- 每个配体有独立输入、配置、日志和结果；
- 每个配体的 config 必须使用队列冻结的六项适用高级参数；`no_refine` 与 `force_even_voxels` 必须通过当前 Vina 能力门禁，并在开始或恢复队列时统一复核；
- 每次 attempt 必须把冻结受体与当前配体按实际字节写入独立目录，在 Vina 启动前和返回后分别核对受体、配体、配置与当前 Vina 二进制的大小和 SHA256；全部一致才允许成功，`attempt.json` 必须记录本次实际使用的输入、配置与 Vina 快照证据；
- 新队列必须冻结并哈希全部九项 `resource_limits`；创建、开始、恢复、归档详情与比较必须共用严格校验，覆盖重试次数、Top N、配体数量、单配体与总输入大小及全部计算边界，且任何限制都不能放宽超过应用硬上限；
- Top N 与原始结果一致；
- 大型项目不一次性把全部结构内容载入前端内存。
- 逐配体 Viewer 不能越出当前 item 的 attempt 目录读取输出，输出哈希变化必须使缓存失效并阻止误展示；
- 历史 Viewer 必须按 `archive_id` 限定归档目录；损坏归档保留可见但阻止详情，旧归档缺输出哈希时显示未完全验证警告；
- 归档详情保持只读，不能恢复为活动队列或修改历史参数；
- 双归档比较必须先核对两个归档的受体与全部配体输入 size/SHA256；只能按冻结 ligand 输入 SHA256 匹配，重复身份必须标为 `ambiguous`；
- 协议指纹必须包含 `max_evals`、`min_rmsd`、`spacing`、`verbosity`、`no_refine` 和 `force_even_voxels`；仅当协议指纹相同、身份唯一、两侧成功且评分与排名有效时计算“对照－基线”差值；协议不同只并排显示，且比较不能写入项目或归档；
- 批量报告必须从当前终态筛选快照生成并列出六项适用高级参数，不能读取后来替换的项目参数。

# 阶段 6：多配体共同对接

## 目标

支持两个已准备配体在同一次 Vina 搜索中共同参与对接，并把联合构象与联合评分安全地呈现给用户。

## 当前状态

**“多配体共同对接（实验性）”已形成 v0.12.2 源码闭环，但本轮不修改版本号、不重新打包，也未进入正式 Release。**

它是独立协议，不是当前串行批量筛选的别名。导入多个配体仍默认进入“多个配体分别运行”的串行批量流程；只有用户显式选择本实验协议时，两个成员才会进入同一次搜索。

## 功能范围

- 一个受体；
- 恰好两个已经准备好的 PDBQT 配体，按用户确认的顺序冻结成员关系；
- 刚性受体、显式 Box、全局对接；
- Vina 或 Vinardo 评分，AutoDock Vina 最低版本 1.2.0；
- Vina 命令使用一个 `--ligand` 参数，后面依次传入两个成员路径，而不是分别启动两个任务；
- 显示各配体原子数与可旋转键；
- 计算总自由度；
- Box 覆盖检查；
- 统一运行；
- 多配体 pose 查看与分别着色；
- 保存成员关系；
- 输出中识别各配体；
- 报告说明其不是批量筛选。

首版明确排除：

- 柔性受体；
- AutoDock4、AD4Zn 或任何预计算 maps；
- `score_only`、`local_only`；
- 水合对接；
- 少于或多于两个成员。

本协议只复用现有 AutoDock Vina、PDBQT、项目记录和 Viewer 基础设施，不新增第三方依赖、外部工具或许可证义务。

## 结果语义

- 每个输出 `MODEL` 是两个成员组成的一组联合构象，不是可以拆成两个独立排名的单配体结果；
- 每个 Mode 只有一个联合评分。不得生成、推断或展示成员 affinity，也不得用两个单配体评分求和代替联合评分；
- 不直接比较成员组成或成员数量不同的联合任务；这种比较没有与单配体批筛相同的排名语义；
- stdout 的结果表可能包含因 `energy_range` 最终未写入输出 PDBQT 的行。构象可用性和成员读取必须以 `out.pdbqt` 中实际存在且带结果记录的 `MODEL` 为准，不能用 stdout 行数补造 pose。

## UI 设计

协议选择中明确区分：

- 串行批量筛选：多个配体分别运行，每个配体有独立任务与评分；
- 多配体共同对接（实验性）：恰好两个配体在同一搜索中运行，每个 Mode 只有联合评分。

共同对接工作区必须显示成员顺序、刚性受体/全局搜索/Vina 或 Vinardo 边界、版本门槛和不支持组合。结果 Viewer 可分别着色、显示或隐藏两个成员，但不能在颜色图例旁放置虚构的成员分值。

## 验收标准

- AutoDock Vina 1.2.0 以下、帮助未声明多路径 `--ligand` 或版本不可确认时，在启动前阻断；
- 命令严格为一个 `--ligand` 后跟两个有序输入路径，并显式指定联合输出文件；
- 官方 5X72 两配体案例已于 2026-07-28 使用仓库随附 AutoDock Vina 1.2.7 完成源码级真实全链路；命令、成员顺序、双成员 Viewer、评分表和报告均通过，官方参考输出 SHA256 `9fd1901bb52d0c767674fdd6e926f749e9995a35aa5b51e0318fd9e6f6922764` 可解析为 7 个双成员 Mode，最佳联合评分 -19.043 kcal/mol；
- 结果中能区分每个配体；
- 输出不会被错误解析成单一配体；
- stdout 行数多于输出 `MODEL` 数时，界面只把实际写入 `out.pdbqt` 的 Mode 标记为可查看；
- 联合评分不会被拆成成员 affinity，不同成员组合或成员数不会显示直接比较结论；
- Box 覆盖不足时给出明确门禁或警告，自由度过高时给出成本提示；
- 覆盖输入/输出篡改、成员顺序变化、缺少成员、取消与失败恢复、历史项目兼容以及 Basic/Assisted 安装态 GUI 回归。

# 阶段 7：AD4Zn 专用协议

## 目标

支持 Zn 金属蛋白的专用 AD4Zn 对接流程。

## 当前状态

**AD4Zn beta 已进入当前源码工作树，但尚未修改版本号、重新打包或进入正式 Release。**

它不是新评分函数：DockStart 生成 TZ 受体，使用用户提供的 `AD4Zn.dat` 与 AutoGrid4 4.2.7+ 生成专用 maps，再由 Vina 以 `--maps <prefix> --scoring ad4` 运行。标准 AutoDock4 maps 基础设施继续独立存在，两种协议不能静默互换。

## 功能范围

### 7.1 Zn 环境识别

- 检测 Zn，并独立列出其他金属；
- 按 v1.2.7 `zinc_pseudo.py` 固定参考的距离键图、羧酸加权代表点和 1-2/1-3 排除列出附近 N/O/S 配位原子和残基；
- 忽略已有 TZ，并把用于协议的 Zn 电荷置零；
- 只有恰好三个受体配位方向且保留一个稳定的开放四面体方向时，才在距 Zn 约 2.0 Å 处生成一个 TZ；近共面位点直接要求人工处理；
- 目标 Zn 的 4.5 Å 邻域含其他金属时阻止自动生成；不把多核位点或 Mg、Fe、Ca 等其他金属自动当成 Zn 协议，未生成 TZ 时硬阻断，不降级到标准 AD4。

### 7.2 TZ 与参数

- 准备项目内独立 TZ 受体，保留原始受体不变；
- 用户从固定上游参考取得并选择 `AD4Zn.dat`；项目复制用户触发的副本，校验受支持关键参数与 GPL 声明，并记录本机来源路径、实际 SHA256、许可证 ID、支持配置和上游参考；
- 生成包含 AD4Zn 专用 `nbp_r_eps` 覆盖的 GPF；
- 仅允许 AutoGrid4 4.2.7 或更高版本，GLG 必须显示成功完成；
- 生成独立 `ad4zn_*` maps 资产并保存 manifest；
- 验证 TZ/Zn 几何、参数、GPF、全部 maps、工具版本和文件 SHA256。

### 7.3 专用报告

记录原始受体与 TZ 受体、Zn、配位残基、TZ、参数文件来源/许可证/hash、GPF、maps、Box、AutoGrid/Vina 证据、用户确认项和科学边界。scores 与报告使用 AD4Zn 专用文件名，不覆盖标准 AD4 或 Vina/Vinardo 结果。

## UI 设计

AD4 顶层协议中保留“标准 AD4 / AD4Zn beta”二级选择。AD4Zn 页面提供站点状态、TZ 几何、参数文件、AutoGrid 兼容性和显式确认清单；准备完成不等于 maps 就绪，只有整个 maps manifest 通过门禁后才允许运行。

用户必须确认目标 Zn、配位环境、质子化、水、辅因子、TZ 几何和“仅限 Zn”。确认绑定受体 SHA256 与站点，输入变化后自动失效。

## 许可证与分发边界

`AD4Zn.dat` 文件自身声明 GPL-2.0-or-later，不随 DockStart 仓库、Basic 或 Assisted 安装包分发，也不由应用静默下载。用户从 AutoDock Vina v1.2.7 固定上游参考自行取得并选择；项目会为可复现性保存副本，并记录本机来源路径、实际 SHA256、许可证 ID、受支持配置和上游参考。分享含该副本的项目时由分享者履行 GPL 再分发义务。未来若提供应用内下载或离线组件包，必须先单独完成 GPL 源码提供、notice 与再分发方案审查。

## 验收标准

- 官方 1S63 TZ 坐标参考已经达到零误差；正式发布还需完成其 AutoGrid/Vina 全链路与更多 Zn 基准；
- 非 Zn 金属不会误进入协议；
- 缺失 AD4Zn 参数时阻止运行；
- AutoGrid4 低于 4.2.7、GLG 未成功完成、TZ 缺失或几何异常、参数/GPF/maps/hash 不一致时阻止运行；
- run 前后可以复核原始受体、TZ 受体、参数、GPF、maps 和工具证据；
- 报告不泛化到其他金属体系。

当前源码闭环不等于完成上述发布验收。正式 beta 发布仍需 1S63 全链路、不同单核 Zn 环境、多核阻断、失败路径、历史项目、Basic/Assisted 干净安装和 GUI 回归；升为 stable 还需更多样本和明确的失败解释。TZ 是几何伪原子，AD4Zn 分值不能与标准 AD4、Vina 或 Vinardo 直接比较，也不能替代实验验证。

## 9. 风险与控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 功能堆叠导致界面复杂 | 初学者无法使用 | 协议分类、逐级披露、默认流程不变 |
| 项目 schema 频繁变化 | 历史项目损坏 | 版本化、迁移备份、未知字段保留 |
| 批量任务占满 CPU | 系统卡顿 | 总 CPU 上限、并发限制、暂停/取消 |
| 配体库规模过大 | 前端卡顿 | 分页、虚拟列表、延迟加载 |
| AD4 maps 错配受体 | 科学结果无效 | 哈希绑定、manifest、变更自动失效 |
| 柔性残基选择错误 | 搜索空间失控 | 数量限制、结构检查、显式确认 |
| 大环被误当普通配体 | 结果不可解释 | 自动检测、专用协议、断环记录 |
| 金属体系被过度泛化 | 误用 AD4Zn | 仅限 Zn、人工确认、专用提示 |
| 自定义权重破坏可比性 | 分数误读 | 实验性标签、独立结果、禁止混排 |
| 第三方许可证问题 | 无法合法分发 | 组件级审查、源码材料、notices |
| 运行被中断 | 项目状态不一致 | 原子写入、任务状态机、恢复检查 |
| 高级功能测试不足 | 错误进入 Stable | maturity 分级、实验性隔离、基准门禁 |

## 10. 成熟度管理

```text

developer
```

完整 UI、文档、自动化测试、安装态测试、科学回归、可恢复运行和清晰报告。

仅用于调试或插件开发，不面向普通用户。

## 11. 基于 v0.12.0 Release 与 v0.12.2 源码实际状态的版本路线

旧路线以“高级协议尚未开发”为前提，已经不适用于当前代码。重新规划时必须先承认以下事实：

- 当前 `project.json` 仍是 schema v1；柔性受体、大环准备、批量筛选和 AD4 maps 通过向后兼容的扩展字段保存，不能把 v0.12.0 写成“schema v2 已完成”。

### 11.2 已进入源码主链但未分配发布版本

`score_only`、`local_only` 与首批七项高级 Vina 参数已完成项目持久化、运行前检查、命令生成、运行快照、结果解析和 Markdown 报告接入；串行批量全局对接也已继承其中适用的六项参数。其中 `local_only` 的第二批定量比较也已完成。这里的“进入源码主链”不等于已发布：

- `score_only` 只评价输入姿势，不产生新构象或排名表；
- 新准备的 `local_only` 先以相同冻结输入与配置运行 `score_only` 基线，再运行 `local_only` 并输出 `optimized.pdbqt`；它仍不是全局对接；
- 结果记录输入与优化后评分、能量项和“优化后－输入”差值，负值不被解释为真实结合改善；
- 姿势位移按严格原子身份在同一受体坐标系直接计算，不做刚体对齐；它不是共晶参考 RMSD，也不生成多构象排名；
- Viewer 可在同一场景安全叠合本次 run 冻结的受体、输入快照与优化后姿势，或单独显示任一姿势；旧单阶段 run 继续可读但不伪造输入基线；
- 帮助页、新建项目页和项目总览已有评分/局部优化入口；文件来源与科学任务正交保存，统一复用现有准备、运行、结果和报告页面；
- 评价模式要求用户在同场 3D 视图确认输入姿势；确认绑定本次运行实际使用的刚性受体、可选柔性侧链与配体 SHA256，替换输入或重建柔性受体后自动失效，并冻结到新 run 的协议快照；
- Vina/Vinardo 可选 autobox，并要求稳定版 Vina 1.2.3 或更高版本；AutoDock4 maps 使用既有 maps 网格，不能同时启用 autobox；
- `max_evals`、`min_rmsd`、`spacing` 与 `verbosity` 按协议和运行模式写入；串行批量全局对接把这些值冻结到队列、逐配体 config、整批报告和归档协议指纹；网格资源保护与详细局部优化日志解析已经接入；
- `no_refine` 与 `force_even_voxels` 默认关闭，仅适用于 Vina/Vinardo；启用后会写入单次 run 或批量队列的不可变配置和报告，并进入批量归档协议指纹；AutoDock4 maps 明确显示不适用；
- `unbound_energy` 默认留空，仅适用于 Vina/Vinardo、刚性单配体 `score_only`；显式 `0` 与留空分开保存，只接受有限数值。新生成的 run 先核对日志 SHA256，再核对第 (4) 项与快照以及 `(1) + (2) + (3) - (4)` 能量平衡；生成后的 `evaluation.json` 在读取与报告前再次核对 SHA256；
- 需要门禁的专家项由当前 Vina 的 `--help_advanced` 精确声明与最低安全版本共同门禁；批量队列启用专家开关时使用相同门禁，并在每次开始或恢复队列前统一复核；每个 attempt 在 Vina 启动前和返回后都会核对本次受体、配体、配置与 Vina 二进制的大小和 SHA256，归档详情及比较继续复核保存的 attempt 输入与配置，但不会复制 Vina 二进制本身。`unbound_energy` 以稳定版 1.2.4 为最低门槛，同核心号预发布版不通过。准备时记录能力证据，执行前再次核对，不能因替换可执行文件绕过；
- 旧项目继续默认 `dock`，不会因打开新版源码而自动改写；
- `randomize_only` 和安装态科学回归仍未完成。

本项尚未绑定新版本号，未改变 v0.12.0、v0.12.x 或后续版本的发布状态。当前源码树已经过 Vina 1.2.7 真实双阶段回归，并覆盖基线失败、阶段间取消、关键文件篡改和旧 run 兼容；只有继续完成 Basic/Assisted 安装态验证、用户文档与发布材料后，才能进入正式版本表。

Vina/Vinardo 预计算 maps 也已进入同一源码维护线，但它是网格资产与运行语义扩展，不是新评分算法：

- 使用当前 Vina 的 `--write_maps` 生成，或导入 DockStart manifest / 用户确认来源的 raw maps；
- manifest 绑定受体、请求 Box、实际网格、评分函数、Vina binary 与全部 map SHA256；
- 激活前以当前配体运行 `--maps ... --score_only` 兼容性探测；
- prepared run 冻结 maps、manifest、受体溯源快照、配体和配置，执行前后均复核；
- 实际运行不传 `--receptor`，属于 `grid-only / no-refine` 等价语义；
- 当前只允许刚性受体、单配体、全局对接，不与柔性、评价任务、autobox 或批量筛选混用。

2026-07-28 已用随附 Vina 1.2.7 分别完成 Vina 与 Vinardo 的真实生成、复用、结果解析和报告回归。它仍需经过 Basic/Assisted 安装态、历史项目和 GUI 发布门禁，不能据此声明现有 Release 已包含。

AD4Zn beta 也已进入源码主链，但属于另一条显式协议：

- 只接受 Zn，不把其他金属泛化为 AD4Zn；
- 只有恰好三个受体配位方向并存在开放四面体方向时生成 TZ；没有 TZ 时阻止运行，不回退为标准 AD4；
- 使用用户提供的 `AD4Zn.dat`；DockStart 不随仓库/安装包内置或自动下载，用户选择后复制到项目并记录本机来源路径、实际 SHA256、GPL-2.0-or-later、支持配置与固定上游参考；
- AutoGrid4 最低版本为 4.2.7，专用 GPF、GLG 成功状态、maps 和 manifest 必须共同通过；
- Vina 仍使用 `--maps` 与 `--scoring ad4`，协议并未修改 Vina 评分函数；
- 原始/TZ 受体、参数、GPF、maps、工具和用户确认进入不可变 run 证据，结果与报告同标准 AD4/Vina 隔离。

这一闭环仍需 1S63、多样本、失败路径、历史项目、干净安装和 GUI 发布门禁。源码存在不等于 v0.12.0 或任何已发布安装包包含 AD4Zn beta。

多配体共同对接也已进入源码主链，但保持 Experimental：

- 最低要求 AutoDock Vina 1.2.0，并确认运行时支持 `--ligand` 多路径输入；
- 只接受恰好两个已准备 PDBQT、刚性受体、显式 Box、Vina/Vinardo 与全局对接；
- 命令只出现一个 `--ligand`，其后按冻结成员顺序传入两个路径；
- 每个输出 `MODEL` 是一组联合构象且只有联合评分，不生成成员 affinity，不直接比较不同成员组合或成员数量；
- Viewer 可用 Mode 只以 `out.pdbqt` 实际存在的 `MODEL` 为准，不能用可能更长的 stdout 结果表补造；
- 不与柔性受体、AD4/AD4Zn/maps、`score_only`、`local_only` 或水合对接组合，不新增第三方依赖或许可证组件。

官方 5X72 案例已于 2026-07-28 用仓库随附 AutoDock Vina 1.2.7 完成源码级真实验收：一个 `--ligand` 后跟两个有序路径、联合解析、双成员 Viewer、评分表与报告均通过；官方参考输出 SHA256 `9fd1901bb52d0c767674fdd6e926f749e9995a35aa5b51e0318fd9e6f6922764` 可解析为 7 个双成员 Mode，最佳联合评分 -19.043 kcal/mol。之后仍需失败恢复、历史项目、Basic/Assisted 干净安装和 GUI 门禁。

### 11.3 暂不绑定版本号的候选能力

以下能力保留，但在基准、工具链、数据模型和许可证边界明确前，不再提前占用 v0.16–v0.22：

- `randomize_only`、自定义评分权重等其余专家参数；
- 水合对接；
- 批量 AD4 maps 与柔性受体 AD4；
- 自定义权重、Python API 和协议插件。

schema v2 也不再作为一个脱离需求的版本目标。只有现有 schema v1 无法安全表达已批准的新协议时，才单独评审迁移；迁移必须提供旧项目备份、只读兼容、失败回滚和跨版本测试，不能为了版本编号而改写用户项目。

每个正式版本仍只完成一个可独立验收的能力闭环。候选能力通过技术验证后再分配版本号，避免用远期编号制造已经承诺交付的错觉。

## 14. Definition of Done

一个新协议只有满足以下条件才能标记为完成：

- 用户可从界面创建该协议项目；
- 输入要求清楚；
- 缺失工具可以检测；
- 结构准备可追踪；
- 参数有默认值与解释；
- 运行前检查可以阻止明显错误；
- 命令使用参数数组构建；
- 每次运行生成独立快照；
- 运行可以取消；
- 异常中断可恢复或明确标记；
- 输出可以解析；
- 结果可在 Viewer 中查看；
- 报告可以导出；
- 科学边界明确；
- 示例可运行；
- Basic/Assisted 支持边界明确；
- 自动化测试通过；
- 安装包验收通过；
- 文档和许可证材料完整。

## 17. 总结

DockStart 下一阶段的关键不是“把 Vina 的所有参数全部搬到界面”，而是：

> 用清晰的协议、可靠的准备流程、严格的运行前检查、可恢复的任务系统和可追溯的结果记录，把 Vina 的高级能力整理成真正可用的现代化科研工作流。

整个扩展过程应坚持：

- 默认流程简单；
- 高级能力分层；
- 本地优先；
- 开箱即用；
- 科学边界明确；
- 历史项目安全；
- 每阶段可发布；
- 每项功能可验收；
- 不用表面完整代替实际可靠。

最终目标是让 DockStart 从当前的标准对接工作台，逐步成长为覆盖 AutoDock Vina 主要能力、适合初学者与科研用户长期使用的一站式本地分子对接平台。
